## §1 The P2-2d `ell_q = 0` finding was a DIAGNOSTIC artefact, not an inert lever — correction

The user forwarded the implementer's diagnosis of why `ell_q` was 0 on every scored onset row in the
P2-2d exponent map: "the flux length is only produced after the surface has receded (first non-zero at
k_top 11, t = 36.5 s); columns that exit the loop before the flux block keep the initialised zero".
Checked against source and the leg data. **The diagnosis is wrong, and so was my 10-10 review finding
(c5) that rested on the same column.**

**What the data actually show** (`expmap/grimsel_full_m20_q500/run_removal_events.csv`, 9216 rows):
`ell_q > 0` on exactly 1152 rows, and those are precisely the rows with `col_j <= 11` AND `k_top <= 11`
(1152 of 1152); every row with `col_j >= 12` is 0 at the same `k_top` (1152 of 1152). Same at q = 800
(3168/3168 split on `j <= 11, k <= 11`). The q = 300 hole never gets below `k_top 18`, so it never
enters that region at all — that is the "dead leg". A physical mechanism does not split the columns
in half by `j`; an MPI box does. With `amr.n_cell = 24^3`, `max_grid_size = 24` and 4 ranks AMReX
chops the one box into z-halves × y-halves; rank 0 (the IO processor) owns `j in [0,11], k in [0,11]`.

**The defect.** `Removal.H` fills the per-column diagnostics `rc_Tsurf, rc_ell, rc_h_f, rc_Tbar,
rc_flag, rc_qrat, rc_ellq` inside the per-box MFIter loop (:1389 → :1609-1611), owner-written, then
collapses them with `ReduceRealSum` at :2202-2207 — **`rc_ellq` is missing from that block** (it was
appended in P1g-3 and never added to the reduce). The CSV is written by the IO processor (:3543) from
its own local vector (:3651), so the `ell_q` column reads the true value only when rank 0's box holds
the firing column's top cell, and 0 everywhere else. This is exactly the "per-box gather read without
reduction" class the P2-2d packet's own lock list names (P1g-2c).

**The lever itself is fine.** `surf_ellq_col` is built in `BuildSurfaceTColumns` (`MMWSpalling.H:3631`)
from rank-reduced inputs (`Ttop`, `T1`, `Ktop` all `ReduceRealSum`'d; `flame_h` is the global
`assign(ncols, h_conv)` under the constants path) and is identical on every rank. The column loop has
NO early exit — every column reaches the flux block. The two fallback counters (`len_fb_h0`, `len_fb_q0`,
non-extensive ⇒ rank 0's value, and rank 0 loops over all 576 columns) read 576 on step 1 only
(`flame_h` not yet filled — harmless) and 0 on all 3599 later steps. With the key on and neither
counter firing, `ell_flux > 0` on every column, so `WeibullSizeFactor` DID act at every onset. The
first visible value, 2.49 mm at k_top 11, is just the first firing inside rank 0's box; it is the same
order as the `V_ref` anchor's 2.58 mm.

**What this does to the P2-2d rejection.** Ground 1 (lever inert at onset ⇒ exponent unattributable)
is WITHDRAWN. Grounds 2-4 stand unchanged: the regime-1 depth scan reads the unscaled flaw under
`flux`; (c2) 7.73 µm has no reducer; the `cell` control ran with `weibull.enabled` off. The exponent
map's numbers are therefore live after all — including the q = 300 legs — and the "live 2-point slopes
(500→800)" re-reading in the 10-10 note was itself the artefact. The map should be re-scored as a
3-point slope per m once the column is fixed, and the "q = 300 onset equals the draw-only level" claim
re-examined with a correctly reduced column rather than taken as proof of inertness.

**Fix** (one line, for the implementer): add `amrex::ParallelDescriptor::ReduceRealSum(rc_ellq.data(),
ncols);` to the block at `Removal.H:2202-2207`. Then the reviewer's assertion "`ell_q > 0` on the first

computable from the initial flat surface" change is unnecessary — it already is — and would alter a
path that is correct. ⚠ Any diagnostic appended to the `rc_*` family must be added to BOTH the assign

User asked, reading the description page's Section 3, whether the surface temperature should be

`PerCellRemoval` (:1542) → swap → conduction (`BuildFlameColumns` at :2034 inside it) → `InvertHtoT`

corrected and republished as rev 3 at the same URL. Note: the user has renamed the source to
`Claude_markdowns/htmls/general_plan.html`; the 10-11 file no longer exists.

**The lag that does exist is the other way round.** Removal does not refresh `surf_T_col` (no writes
in `Removal.H`; only `BuildSurfaceTColumns` writes it), and the conduction at the end of the same step
reads it through `SurfaceRobinT` (:3834) at every Robin site (kernel :2225, lateral :2313, march
:3384/:3435, side :3924, ledger :4341/:4401) under `robin_form = surface` (Meier). So a column that
fired is heated for one step at its PRE-firing T_s. Post-flake surface rise is e^{-c_f} = 0.67 of the
old rise ⇒ T_s overestimated by ~0.33·(850−293) ≈ 185 K for one step; against T_g − T_s of several
hundred K that is roughly a quarter of one step's flux (and losses overestimated in the same
direction). Firing interval per column ≈ h_f / v ≈ 0.3 mm / 0.9 mm s⁻¹ ≈ 0.35 s ≈ 22 steps at 16 ms ⇒
**systematic under-delivery of order 1 %**, halving at 8 ms (dt-dependent). ESTIMATE, not measured.
Kant `cell` form unaffected (reads the remapped cell directly). Cheap fix for the planner: re-run
`BuildSurfaceTColumns` (or only the fired columns) after `PerCellRemoval` and before the conduction;
the remap preserves the exponential's ℓ, so the two-cell x is unchanged and the refreshed T_s is
exactly T0 + (T_s − T0)e^{−h_f/ℓ}. Added to the page's "Smaller items". Also corrected on the page:
the two sentences that called the size term inert (§1 above). No code touched.
